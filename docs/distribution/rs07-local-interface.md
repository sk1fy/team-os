# РС-07: рабочий интерфейс распределения

Рабочие маршруты `/distribution`, `/distribution/:groupId` и `/distribution/new` используют HTTP API TeamOS backend. Подмена распределения локальными fixtures отсутствует даже при настройках других модулей в mock mode. Актор и сотрудники также загружаются через HTTP с отдельными query keys, чтобы не использовать кеш демо.

## Что реализовано

- **07.1.1:** список групп, состояние, воронка и этап конкретного подключения, серверная доступность, ожидание и ошибки. Неподключённый аккаунт, пустой список, загрузка, отсутствие прав и недоступный источник показаны явно. Правила загружаются страницами по 100, без потери правил после первой страницы.
- **07.1.2:** отдельный режим настроек группы, выбор подключения/воронки/этапа, порядок участников, выключение отдельных участников, round-robin, keep-current по умолчанию, часовой пояс компании. Сохранение группы и правила использует фактические ревизии. Несколько исторических правил одной группы блокируют редактор с объяснением. Настройки остаются смонтированными при переключении к очереди, поэтому черновик сохраняется.
- **07.2.1:** основная очередь и очередь группы, серверные фильтры состояний/группы/периода, страницы по 25, причины, длительность, планируемый или подтверждённый ответственный. Детали: текущий/предыдущий ответственный при наличии достоверного сопоставления, история, операция и версия результата, проверенная сервером ссылка amoCRM. Отсутствующие сведения показаны как недоступные.
- **07.2.2:** ограниченный polling раз в 15 секунд только на открытом видимом экране при наличии сети; отмена чтения через AbortSignal; серверный перечень разрешённых действий. POST не повторяется автоматически, в том числе после 401. При неизвестном результате сохраняется идентификатор и точное тело запроса; отдельная кнопка восстанавливает его результат. При доказанных 400/403/409 запрос снимается с ожидания и показывается отказ.
- **07.3.1:** статистика с сервера, nullable counters при невозможности подтвердить права/источник, часовой пояс компании. Доступность сотрудников исключительно из серверного расписания. Демо-формула нагрузки, симуляция назначений и удаление реальной истории отсутствуют в рабочих экранах.
- **07.3.2:** адаптивные карточки, подписанные поля и действия, клавиатурное переключение вкладок стрелками, roving focus, Radix Modal с возвратом фокуса к сделке или текущей вкладке после исчезновения строки.

## Сохранение и ограничения

Группа, общий часовой пояс и правило сохраняются отдельными API-запросами: это не общая транзакция. При частичном успехе сообщение перечисляет уже сохранённые шаги. 409 и фоновые ошибки чтения не уничтожают поля. Пользователь может обновить версии, проверить свой черновик и осознанно повторить сохранение. Неизвестный ответ создания группы блокирует повторное создание: сначала необходимо проверить список групп.

При недоступном справочнике amoCRM запуск блокируется, но существующее неизменённое правило можно приостановить. Изменение точки распределения использованного правила сервер запрещает: требуется отдельная новая группа/правило, чтобы сохранить историю и границы активации.

Разрешения проверяет сервер при каждом действии; role UI лишь скрывает управление. Идентификатор неизвестного действия сохраняется на время работы экрана, после полной перезагрузки необходимо сначала проверить текущее состояние. Интерфейс не обещает внешнего exactly-once или атомарности GET→PATCH amoCRM.

## Локальный запуск

Настроить `VITE_API_URL` на локальный gateway (`http://localhost:8080/api/v1` по умолчанию) и `VITE_API_MODE_AUTH=http`, `VITE_API_MODE_ORG=http` для согласованного режима всей оболочки, затем `npm run dev`. Для реального рабочего API нужны локально поднятые backend/БД и подходящий авторизованный тестовый пользователь. Отсутствие подключённого аккаунта amoCRM показывается явно, без генерации рабочих сделок.

Автоматическая проверка UI не требует учётных записей amoCRM:

```sh
npm run e2e:distribution
npm run build
npm run test
npm run contract:check
```

`playwright.distribution.config.ts` запускает Vite на `127.0.0.1:4174`. Только `e2e/distribution.spec.ts` перехватывает HTTP для детерминированных тестовых данных. Это браузерная проверка интерфейса на согласованных контрактах, **не** проверка реальных Core/TeamOS/amoCRM сервисов. Сценарии: настройки → ожидание → отправка → безопасная ошибка/повтор → подтверждение на 1440/390 px, отказ прав, отказ источника, 409 + фоновый 503 с сохранёнными полями, receipt 202 без преждевременного завершения, потерянный ответ и повтор точного запроса, пауза при отказе amoCRM. Проверка axe не допускает critical/serious нарушений в main.

Скриншоты создаются в `test-results/distribution-{1440,390}-{settings,queue}.png`; это ignored тестовые артефакты. Узкий снимок очереди может использовать повышенную высоту viewport для показа карточки целиком; проверенная ширина остаётся 390 px.

## Следующая проверка

Тестовый сервер: отдельные базы/домены, HTTPS gateway и приватный Core↔TeamOS транспорт, конфигурация capability и явные grants, серверные миграции и точные версии обоих сервисов. Можно сначала проверять с контролируемым CRM fixture, затем подключить тестовый аккаунт.

Тестовый аккаунт amoCRM: OAuth установленной тестовой интеграции, искусственные сделки, проверенные сопоставления 2–3 сотрудников, отдельная воронка/этап и согласованные графики. Проверить реальные вебхуки, ответственное назначение, повтор, паузу и восстановление после сбоя. Рабочие клиентские данные не нужны. Эта живая проверка пока не выполнена и не заменяется локальным UI fixture.
